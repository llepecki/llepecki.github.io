The app exists locally; this document specifies the intended behavior and has absorbed the one-time implementation review, which was deleted on 2026-09-26 once its items shipped. `CLAUDE.md` is binding for shared layout, code, localization, and accessibility conventions. `fractions/index.html` is a visual-family reference, not a source of interaction requirements. Where this document is more specific about Factor Workshop, follow this document.

## 1. Product decision and learning target

Build one bilingual, self-contained app for roughly ages 9–12. English uses **GCD** (greatest common divisor) and **LCM** (least common multiple); Polish uses **NWD** (największy wspólny dzielnik) and **NWW** (najmniejsza wspólna wielokrotność). The visible title is **Factor Workshop** / **Warsztat dzielników**. Spell out the selected term on its first screen and whenever the algorithm changes.

**The taught algorithm for both results is prime factorization.** The child breaks each input into prime tiles and matches equal tiles across the inputs:

- GCD/NWD: multiply **one tile from every matched pair**. If nothing matches, the result is `1`.
- LCM/NWW: multiply **one tile from every matched pair plus every unmatched tile**. A shared pair is counted once, not twice.

The child should understand the result, not just follow the rule. Equal-size groups show why the GCD divides both inputs. Two aligned jump lanes show why the LCM is the _first positive_ number reached by both patterns. Using `12,18`, the child should be able to explain `GCD = 2 × 3 = 6`, `LCM = 2 × 3 × 2 × 3 = 36`, `12 = 2 × 6`, `18 = 3 × 6`, and `36 = 3 × 12 = 2 × 18`.

This is a deliberate choice of method, not an accidental omission: the Euclidean algorithm, long-division notation, Venn diagrams, three-number cases, and general prime-factor curriculum are outside v1. Do not label the equal-group picture as Euclid's algorithm. The Polish grades IV–VI curriculum specifies prime-factorization for NWD/NWW [1]. If the product owner wants Euclid taught as a named algorithm, that is a scope change requiring approval.

## 2. Learning flow and scope guardrails

The app has exactly four experiences: a **short interactive tutorial that introduces both algorithms**, **guided practice** for the selected algorithm, a separate **Challenge** for the selected algorithm, and **Your numbers**, a Guided-style board for a pair the child picks (§4.3). The tutorial precedes the first selection unless explicitly skipped. Challenge and Your numbers are available after selection without a lock or timer. The same workbench and two action phases are reused throughout; Challenge does not introduce a second game system.

The learning sequence is: recognize a factor → learn that only `1` and a prime itself divide it exactly → break one number into prime tiles → match equal tiles → use the matched and unmatched tiles differently for GCD and LCM → verify with groups or jumps → solve without prompts in Challenge. The first tutorial interaction must be **splitting a number**, not selecting from already-split answers.

Eight fixed guided pairs per algorithm, and five Challenge tasks per algorithm drawn per run from the pool in §6, are in scope. There are no accounts, backend, required audio, typed answers, timer, coins, streaks, avatars, achievements, or penalty for retries. One progress count is enough; Your numbers keeps no count. Do not add a mandatory “prove” question after every guided task: on success the proof is a concise visual explanation. Challenge tests the result **before** revealing the numerical answer.

Add optional pointer dragging to the tile-assembly phase because physically connecting and collecting prime tiles suits the workbench metaphor. The child must still be able to finish every tutorial, Guided, Challenge and Your numbers task with single taps/clicks or keyboard alone. Dragging is a parallel way to commit the same mathematical actions, not a new phase, scoring method, or prerequisite [5]. The prime set is `{2,3,5,7}` (7 added 2026-09-25) and splitting is primarily a drag onto the amber circle, with a two-step tap as the keyboard-reachable equivalent; do not add a second drag target to that phase.

Equal-group bars explain GCD but become tedious as a search method. Parallel jumps explain LCM but become dense at larger values. Keep each as a brief meaning check, not the main computation. A Venn diagram of _distinct_ primes can hide multiplicity (`8 = 2 × 2 × 2` needs three copies). Euclidean tiling would add a second GCD procedure without a matching LCM procedure. Paired prime tiles preserve repeated factors and provide one action grammar for both algorithms. This is an instructional hypothesis; test it with children before claiming it is more engaging or effective than alternatives.

## 4. Exact experience and state transitions

### 4.1 Tutorial, then algorithm choice

On first visit open the `intro-mode` panel with two scenes in this order: GCD/NWD, then LCM/NWW. A third panel state is algorithm choice. On later visits open directly at choice. `Skip tutorial` goes to choice from either scene; `Replay tutorial` resets both scenes to their initial states. Store the guarded, versioned `gcdlcmIntroSeenV2` flag when the child reaches choice, whether through completion or skip. Storage failure must not block use. `Previous` returns to the preceding scene with its completed actions preserved; `Next` is disabled until the current scene's required interaction is complete. The choice screen has no `Next` button. The tutorial is short because each scene has one example and no extra quiz.

**Scene 1, GCD/NWD, `12` and `18`.** The board initially shows whole `12` and a large `2` button. The first line teaches “A factor helps make a number: `2 × 6 = 12`.” The flowchart (§5) opens with `Split A` current. Child taps `2` to perform `12 ÷ 2 = 6`; the rail's invariant line reads `12 = 2 × 6` and the `All primes now?` diamond answers `No: 6 left`, looping back to `Split A`. A single clearly marked demonstration unfolds the remaining factors (`6 = 2 × 3`, `18 = 2 × 3 × 3`) without treating that demonstration as a child success; every demonstrated split re-renders the chart, so the child watches `Split A` loop, `All primes now? Yes` hand over to `Split B`, and its test hand over to `Pair them`. The panel shows `stepSplitInfo` for the row being split while the demonstration runs. The next lines teach “`2` and `3` are prime: only `1` and the number itself divide them exactly” and `stepMatchInfo`. The child drags one `2` onto the other `2`, or taps the two tiles, then repeats for `3`; `Any equal tiles left?` answers `Yes` before each pair and `No` after the second, `GCD or LCM?` answers `GCD`, and `Multiply the shelf` becomes current. Each pair sends **one** copy to the shared shelf; the two unmatched tiles remain visible. Only after both pairs does the shelf reveal `2 × 3 = 6`. Two equal-width group bars show `12` as two groups of `6` and `18` as three groups of `6`. Finish with “Six is the largest group size that fits both with no leftovers.” Then enable `Next`.

**Scene 2, LCM/NWW, `4` and `6`.** Show `4 = 2 × 2`, `6 = 2 × 3`, and remind the child that these are prime tiles; the four split nodes read `Given` and the chart opens at `Pair them`. The child pairs one `2` from each row by dragging either `2` onto the other or tapping both; then, with `lcmRule` shown above the prompt, `GCD or LCM?` answers `LCM` and `Add every leftover tile` is current while the child drags the unmatched `2` and `3` onto the `Left over` shelf or taps each tile. The shelf shows `2 × 2 × 3` and reveals `12` only after both leftovers are added. Under it, two aligned lanes land at `4, 8, 12` and `6, 12`; mark `12` as their **first positive** common landing. Finish with “Keep one shared tile and every leftover tile. Both jump patterns first meet at 12.” Then enable `Next` to choice. Do not begin this scene with the pair already made.

**Choice.** The stage shows two large cards that are the buttons (2026-09-24: the earlier layout drew inert cards on the stage and put smaller `Learn GCD` / `Learn LCM` buttons in the panel, so users tapped the cards and nothing happened): each card carries its motif (2026-09-25: the GCD card shows two bars of different length cut into cells of the **same** size with the shared unit filled, replacing an earlier drawing that had equal bars cut into different-sized cells, which stated the opposite of a common measure; the LCM card shows two rows of dots at different strides landing together on one larger dot, replacing arcs that filled in solid at a 2px stroke), the label `Learn GCD` / `Learn LCM`, the full term and the two definition lines (`gcdMeaning` + `gcdRule`, `lcmMeaning` + `lcmRule`) as its description. The panel shows only the heading `Choose an algorithm.` (the focus target) and `Replay tutorial`; the stage shows no instruction pill, so the prompt appears once. Selecting a card starts Guided practice at its first unsolved pair. No Challenge or Your numbers controls compete on this choice screen; both are accessible from the practice panel and never locked. Returning via `Switch algorithm` opens choice; it does not replay tutorial.

### 4.2 Guided practice: only two action phases

The current task stays prominent: “Find the GCD of 12 and 18,” for example. Each pair has `split → assemble → result`; only `split` and `assemble` require work. The result state is a visual explanation, **not** a compulsory extra answer. The first guided pair per algorithm uses one non-blocking highlight on a valid prime and a preview connector for the first match. Later pairs remove these cues. No action is committed automatically in Guided practice.

| State      | Allowed action and transition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | What stays visible                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `split`    | Work on the first number, then the second. **Drag a prime button `2`, `3`, `5`, or `7` onto the amber circle**, which is the part still to be broken down. Tapping does the same thing in two steps and never in one: tapping a prime only picks it up — it commits nothing and is silent — and the split happens when the child then touches the amber circle. Tapping the picked prime again puts it back. The rule is that the number is always the thing the child acts on, so the split lands where the child is looking. Issue that tile and update the row's split invariant line. Picking a prime moves focus to the amber circle, which is a tab stop only while a prime is picked up, so the resting Tab order still runs to the prime buttons. When quotient becomes `1`, focus the other input; when both reach `1`, move to `assemble`. A prime that does not divide gives `invalidPrime` when it reaches the circle, drops the pick, and does not change state; a prime dropped anywhere but the active rail cancels. | One line per number: a filled ball in that number's colour, `=`, then its prime factors as hollow green circles and the still-unsplit part as a filled amber circle. There is no trailing tick (2026-09-26): a split can only ever divide exactly, so a mark that can never say no says nothing, and a finished row already reads as finished because its amber circle is gone and every circle is green. A fresh row reads `18 = 18` with the amber circle already on screen, so the child always has a target. The amber circle disappears at `1`. |
| `assemble` | Tap an unpaired tile in either row, then an equal tile in the other row, **or** drag either tile onto the equal tile **or onto the `Shared` shelf** (which pairs it with its first equal unpaired counterpart); keep one copy in the shared shelf. A wrong tap target cancels only the pending selection; a wrong drag target changes no committed work. Both give `wrongPair` feedback. GCD: after all possible pairs, `Check result` succeeds. LCM: after all possible pairs, tap each unmatched tile or drag it onto `Left over` exactly once, then `Check result` succeeds. `Check result` is enabled throughout `assemble`; an incomplete shelf yields a specific nudge and does not reveal the answer.                                                                                                                                                                                                                                                                                                                        | Both source rows with their invariant lines, paired connectors, unmatched tiles, the symbolic product, and a `?` for the numeric result.                                                                                                                                                                                                                                                                                                                                                                                                             |
| `result`   | Show the exact numeric answer, then the group/jump proof led by the algorithm's definition in one sentence (`gcdMeaning`/`lcmMeaning`, 2026-09-26: the definition moved here from the deleted `How it works` disclosure, where it sat two disclosures deep; here the child has the number in front of them). `Next pair` advances. `Start this pair again` returns to fresh `split`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | The finished shelf, the two split invariant lines, one compact proof strip, and the next action.                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

Pair order may vary, but each A tile can pair with only one B tile. In the matching part of `assemble`, enable any unpaired tile in either row that has an equal unpaired counterpart; tapping it selects it, and tapping an unpaired tile in the opposite row commits a pair only if the values match. A different value gives `wrongPair` and clears the selection. Tapping the selected tile again deselects it; tapping another matchable tile in the same row replaces the selection without committing a pair. Dragging can likewise start from either row. Once no possible pair remains, the remaining GCD source tiles are passive; the remaining LCM source tiles become tap-to-add and drag-to-`Left over` controls. For coprime pairs, `assemble` begins with no possible matches: GCD shows an empty shelf labeled `No shared tiles` — said once, on the shelf, and not repeated by the cue (2026-09-26) — and a numeric `?` until checking reveals `1`; LCM requires all source tiles. On a GCD board with an unmade match, an empty shared shelf has **no** `No shared tiles` message. For equal inputs, all tiles pair and LCM has no leftovers. In Guided practice, symbolic factors appear as they are built; the Result shelf's answer slot stays `?` until a complete `Check result`, and the proof appears only once that check succeeds, so the `?` is answered by the check rather than given away beforehand. No experience explains the answer before the result. For GCD, checking early identifies a still-available shared prime. For LCM, checking early identifies the first unmatched tile not yet included. Do not silently add it.

The result proof is never another scored step. GCD uses two aligned equal-group bars, with `A ÷ GCD` and `B ÷ GCD` displayed. LCM uses two aligned jump lanes and shows `LCM ÷ A` and `LCM ÷ B`. Draw only one brief motion when the result appears; it must not block `Next pair`. Progress is `completed / 8`, not a star economy, and it ticks on a correct check rather than on `Next pair`. A correct result puts one factual success line in the panel where the error messages appear (`solvedPair` in Guided and Your numbers, `independentOne` / `withHelp` in Challenge); no emoji, stars or grades. After pair eight, show `Practice again` and `Try Challenge`; `Practice again` resets this algorithm's guided index to pair one without erasing Challenge results.

### 4.3 Challenge: independent transfer on the same workbench

`Challenge` is a separate mode with five tasks per algorithm, drawn per run from the pool in §6, that never repeat a pair of that algorithm's Guided deck. It can be entered at any time from the selected algorithm's practice panel. The board and split/assemble actions are unchanged; no ghosted tile, preview connector, or step-by-step instruction is shown. One compact task sentence and the phase label remain. Two tasks per algorithm start with correctly pre-split source rows, asking the child to apply the _matching/building_ rule without repeating the same division sequence. This is a given starting condition, not automatically earned progress.

In Challenge, the numeric product stays `?`. The **three numeric choices and `Submit answer` are visible from the start of `assemble`**, even before the shelf is complete, so the child can test a hypothesis. With no choice selected, submission shows `chooseAnswer` and does not count. Otherwise the submission checks both the shelf and selected number. If the shelf is incomplete, say what category of tile is missing without showing the answer; the selected choice remains selected. If the shelf is complete but the number is wrong, say to recount the product; do not reveal the answer. The child may retry without a limit or time pressure. A correct submission reveals the result proof and `Next challenge`. One task counts as **independent** only if the first counted submission is correct and no hint or `Show one step` was used. Otherwise it still counts as completed, marked **with help**. A wrong/incomplete counted submission permanently removes independent status for that task in the current run; simple invalid taps do not. At five completed tasks, show `X / 5 solved independently`, plus `Try again` (a fresh draw of five tasks) and `Guided practice`. No stars, grades, leaderboard, or lock.

**Your numbers.** The third button of the experience switch opens a picker on the stage in place of the workbench: the 28 px prompt `customPrompt`, two rows of the twenty-one task values (§6) captioned `customRowA` / `customRowB` as toggle buttons (`aria-pressed`, 52 × 48 px, 20 px mono, A/B tinted when pressed), the 15 px note `customNote`, and a primary `customStart` button enabled once both rows have a pick. A number is disabled when, with the other row's pick, the pair fails the proof rule of §6 (`proofFits`); pressing a picked number again releases it. `Start` opens a Guided-style task for that pair, in the picked order, with the chart, hints, `Undo`, `Start this pair again` and `Check result`; there are no answer choices, no first-pair cue glow and no preview connector. In `result` the primary action reads `customNext` and returns to the picker with the same picks still pressed. Nothing is counted: the panel's progress line is hidden and no summary exists. Switching away parks an unfinished custom board like any other task; with none open, the destination is the picker.

`Hint` in every practice experience (Guided, Challenge and Your numbers) has two presses: first a one-sentence concept cue for the current phase, then a visual highlight of one valid next tile or the primary action if the shelf is complete. A third press reveals `Show one step` **only if a split, pair, or leftover addition remains**; using it commits exactly that one action. If no action remains, stay at tier two and do not reveal the answer. Choose the lowest-valued valid prime or unmade pair, then the lowest-valued leftover, for hints and assisted moves. Any hint press marks the Challenge task assisted; Guided progress has no scoring. Reset the hint level after a committed child action and on a new task, but retain the assisted flag for the current Challenge task. A tutorial demo is never recorded as progress.

If a factor tile is pending from either row, `Hint` highlights an equal unpaired tile in the **opposite** row, and `Show one step` commits that one pair. A hint must not assume the pending tile came from A. Undo first cancels a pending tile from either row.

### 4.4 Navigation, feedback, and deterministic state rules

In practice, panel order is **task → progress → feedback → `Hint`, `Undo` → a collapsed `More` disclosure** holding `Start this pair again`, the stacked `Guided practice` / `Challenge` / `Your numbers` switch, `Switch algorithm` and `Replay tutorial`. `How it works` was removed on 2026-09-26: it was a disclosure inside a disclosure holding a third copy of two sentences the child had already read on the algorithm choice card, and `gcdRule`/`lcmRule` is also the fallback Hint message. `Hint` disables itself at tier 3, where it would only repeat its tier-2 sentence and the help it unlocked is already on screen as `Show one step`. The progress count sits under the task sentence, not inside `More` (2026-09-24: a child played six pairs without once seeing it). It reads `solvedCount`, which counts the current task the moment it is solved rather than when `Next pair` is pressed, and it is hidden for Your numbers and on a summary, whose heading already states the count. `More` is closed by default and stays open or closed for the session; its button carries `aria-expanded` and `aria-controls`. Place the primary action (`Check result` or `Submit answer`) once, adjacent to the workbench; do not mirror it in the panel. `Next pair`, `Next challenge` or `Pick new numbers` replaces the primary action in `result`. The panel carries the task sentence; the phase lives in the stage's flowchart (§5), whose single current node names it, and the 28 px instruction sits above the workbench on desktop and under the current node in the phone's compact card. The panel does not repeat them.

Control visibility is fixed: `split` shows prime buttons but no submit/check button; `assemble` shows selectable factor tiles and either Guided `Check result` or Challenge answer choices plus `Submit answer`; `result` hides prime, tile, and answer inputs and shows only the next/restart actions. Challenge tasks marked `pre-split` enter directly at `assemble`. Numeric answer choices are three mutually exclusive buttons with an exposed selected state (`aria-pressed`); selecting another changes the selection without counting an attempt. Do not auto-advance to `result` when the shelf becomes complete.

Focus behavior is fixed: on first tutorial entry, focus its heading; on starting a new practice task, announce the full task once before focusing the first available action. On entering `split`, focus the first valid prime button for A; after a valid division keep focus on that prime if it still divides the active quotient, otherwise move to the first valid prime for that quotient or the newly active B. On entering `assemble`, focus the first matchable A tile; if there is no possible pair, focus the first LCM leftover or the primary action for GCD. Selecting a tile in either row moves focus to the first equal unpaired tile in the opposite row. After a pair, focus the next matchable A tile, then a leftover, then the primary action as each set empties. Invalid actions keep focus on the attempted control. Successful submission moves focus to `Next pair` / `Next challenge` / `Pick new numbers`; switching experience moves focus to the new task heading. A language switch keeps focus on the language button. **The DOM reading and Tab order is heading/full task → flowchart and instruction (not Tab stops; at ≤720 px the `Show all steps` toggle is the chart's only Tab stop and precedes the stage actions) → stage actions → feedback and secondary panel controls.** Split the current monolithic panel into sibling task-header and secondary-control blocks around the stage in DOM: `<main>` contains task header, stage, then secondary controls. A two-column CSS grid places the task header and secondary controls in the 320 px right column and the stage in the left column on desktop; at ≤720 px it stacks those three blocks in DOM order. This preserves the light chassis's visual geometry while correcting its reading order. A focused tutorial heading must lead by Tab to the first prime or tile action, not to `Skip tutorial`; a focused task heading after an experience switch must lead by Tab to the first available stage action, not to `Hint`. Do not use positive `tabindex` or a keyboard-only shortcut to conceal incorrect DOM order.

Use this grid placement without duplicating any element: desktop columns `minmax(0, 1fr) 320px` and rows `auto minmax(0, 1fr)`; inside the stage, the 300px chart column and the workbench sit 40px apart (2026-09-25, up from 20px); task header in column 2/row 1, stage in column 1 spanning both rows, secondary controls in column 2/row 2. The two right-column blocks share the current white panel treatment and one vertical scroll area for secondary controls. At ≤720 px, use one column and the natural DOM sequence: task header, stage, secondary controls. Tutorial navigation (`Previous`, `Next`, `Skip tutorial`) lives in the secondary-control block, so its Tab stops follow the stage; on the choice screen the two algorithm cards are the stage's buttons, so Tab from the heading reaches `Learn GCD`, then `Learn LCM`, then `Replay tutorial`. The stage's flowchart nodes and instruction are not focus stops. The `<body>` still contains only the shared header and `<main>` before the script.

`Undo` first cancels a pending selected tile, if any. Otherwise it reverts the last committed split, pair, or leftover addition using a state snapshot; the derived phase returns to `split` if an undone split makes factorization incomplete. Undo never erases hints or a counted Challenge submission. It is disabled after success, when there is no prior action, and on the choice screen. `Start this pair again` resets the current board and hint tier, not completed progress. In Challenge it **retains** an assisted/failed-first-submission flag already incurred, so reset cannot restore independent status. Switching algorithm or experience **parks the unfinished task in memory** and opens the last active task in the destination experience, or its first unsolved task if none is active (for Your numbers, the picker). Returning resumes the exact board, selection, hint, and attempt state; switching alone never marks a Challenge task assisted. Completed tasks remain completed for this session. `Replay tutorial` does not reset task progress. If all tasks in the target experience are complete, open its summary, not an undefined next pair.

A refused action also flashes the control the child actually touched: a red ring and a short shake on the prime button for an invalid divisor, on the tile for a mismatched pair, on the primary button for a check or submission the shelf is not ready for, on the selected choice for a wrong Challenge answer, and on the drop zone for a drag the board turns down. The panel sentence stays; the flash is the signal beside the child's hand, and it never replaces the words. Under reduced motion the ring remains and the shake does not run, so the cue is never motion-only. A drag released over empty space commits nothing and flashes nothing, because nothing refused it.

Feedback is one sentence, specific and neutral. An invalid divisor says which quotient does not divide evenly. A mismatched pair asks for the same prime. On incomplete checks, report the lowest-valued unmade shared pair first; only after all pairs are made report the lowest-valued unadded LCM leftover. A wrong Challenge choice asks the child to multiply the tiles again; it does not show the correct number. Use the exact localized templates in §7. Wrong actions preserve all correct work. Announce only committed changes and feedback in a polite live region; do not announce every animation frame. Each committed split, pair, leftover addition, hint step and undo produces exactly one sentence: the arithmetic, the diamond answers the board just gave, and the node reached, e.g. `6 ÷ 2 = 3. All primes now? No: 3 left. Split A.` Selecting or deselecting a tile is silent; the tutorial demonstration announces once when it finishes.

### 4.5 Dragging — the same actions, not a second game

Drag is available in every work phase: `split` (a prime button onto the active rail, tutorial included once the child controls the board), the tutorial's child-controlled assembly steps, and Guided, Challenge and Your numbers `assemble`. It is absent during the tutorial demonstration, `result`, choice, the number picker, and summaries. Never drag the original source tile out of its rail: a pointer-following visual copy moves, while the source remains in place. On success, reuse the **same** pair or leftover-addition state transition as a tap, so pairing still leaves both source tiles visible and adds exactly one shared copy. A completed drag creates one undo snapshot, resets the hint tier like a tap, and never counts as a Challenge answer submission or Hint. A failed or cancelled drag does not change the mathematical board or Challenge independence, but a drop that lands on a real zone and is turned down flashes that zone (§4.4) so it never looks as though the drop went unnoticed.

A prime that divides the quotient issues a tile, one that does not gives `invalidPrime`. A drop on the inactive rail or elsewhere cancels.                                                         | Tap the prime button, then tap the amber circle.                         |

Use Pointer Events (`pointerdown`, `pointermove`, `pointerup`, `pointercancel`) and pointer capture for one active primary pointer; do not use the HTML drag-and-drop API or separate mouse/touch rule paths [8]. On `pointerdown` of a legal source, remember its tile ID, pointer ID, coordinates, and any pending tap selection, but do not mutate the rule state. Movement of at least `8` CSS px starts the visual drag. Before that threshold, release is a normal button tap and must **not** also commit a drag. After the threshold, suppress the synthetic click for that gesture; on release, hit-test the drop target using the pointer coordinates rather than the captured event target. Ignore additional pointers. Apply `touch-action: none` only to currently draggable factor buttons, not the stage, shelves, panel, or page; native page scrolling must still work when a touch begins outside those buttons. Keep non-draggable tap controls at `touch-action: manipulation`.

For a prime drop, the active row's amber circle plus an `8` px halo is the target, and it carries the lit ring. A prime dropped on the other row's amber circle cancels.

## 6. Mathematical rules, the locked Guided deck and the Challenge generator

Only positive integers. Every task input is ≤30 and has prime factors only from `{2,3,5,7}` (7 added 2026-09-25, widening the task values from seventeen to twenty-one). `primeFactors(n)` returns a sorted multiset, but **emitted tiles keep the order the child made them and are never re-sorted** (2026-09-25): each tile appears where it was issued, immediately left of the amber circle, followed by the remainder the row closes itself with. Splitting `30` by `5` and then `2` reads `30 = 5 × 2 × 3`, not `2 × 3 × 5`. Sorting used to run after every split, so a tile the child had just placed jumped left and the line stopped being a record of what they did. Nothing depends on the order: pairing, the shelves, `possiblePairs` and both invariants work from tile values, and the shelf and leftover lists sort themselves for display. For a prime `p` with multiplicities `a(p)` and `b(p)`, the shared shelf contains `min(a(p), b(p))` copies, and the LCM result shelf contains `max(a(p), b(p))` copies. An empty GCD product is `1`; `1` is not a prime tile. `0` is not a candidate for least **positive** common multiple.

The child may choose **any** prime among `2,3,5,7` that divides the current quotient. When a split leaves a **prime** remainder the row closes itself, emitting that prime as a tile and setting the quotient to `1` (2026-09-24, reversing the earlier rule that the prime quotient had to be selected again: naming a prime the child has just demonstrated teaches nothing and costs a tap). There is no `✓` on a finished row (2026-09-26): the split can only ever divide exactly, so the mark could never say no. An invalid choice leaves state unchanged. Pairing consumes one tile from each source row, but both remain visible with a paired state and only one counted copy goes to the shared shelf. Unmatched LCM tiles can each be added once. ## 8. Implementation boundaries and acceptance checks

Keep `gcdlcm/index.html` as a single HTML file with inline CSS and one inline IIFE script, no Jekyll front matter or sidecar runtime files, and no dependency beyond the shared Google Fonts link. Use DOM buttons for prime choices, factor tiles, mode selection, answer choices, and actions; SVG/CSS may draw non-interactive connectors and proof illustrations. Pointer dragging operates on those factor buttons and must call the same pure rule actions as tapping. Avoid an essential canvas-only hit region. Use `textContent` and element creation, never `innerHTML`. Follow `CLAUDE.md` for metadata, canonical and `og:url` `https://lepecki.com/learn/gcdlcm/`, light chassis, versioned storage, focus, and reduced motion. Keep the existing `index.md` hub entry current; this follow-up does not add a second app.

One state object should hold `screen`, `tutorialScene` and its committed demo actions, `algorithm`, `experience`, and an in-memory active-task record for each algorithm/experience combination. Each task record holds `taskIndex`, source quotients and emitted tiles, pairs, added leftovers, pending selection, selected Challenge choice, hint tier, assisted flag, and first-submission flag; completion counts are per algorithm/experience combination. Derive the product, legal moves, and phase from that state. Pure math helpers should include `primeFactors`, `factorCounts`, `gcd`, `lcm`, and `isCompleteShelf`. The answer tables in §6 are test fixtures, not runtime truth. Only `gcdlcmIntroSeenV2` persists across reloads; all task progress is session-only in v1. `Try again` on a Challenge summary draws five new Challenge tasks for the **selected algorithm only**. The Your numbers run per algorithm holds the current picks and at most one task; nothing from it is counted. A page reload restarts task progress at algorithm choice.
